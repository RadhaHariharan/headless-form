# useField

**File:** `src/hooks/use-field.ts`

A standalone single-field hook — internally a stripped-down `useForm` scoped to exactly one value, useful for composing custom inputs, building field-as-a-component patterns, or isolating field logic in a library without requiring a full form. Works unchanged in React Native via `@headlesskit/forms-react-native`, which re-exports it directly.

## Signature

```typescript
function useField<Value, TError = ReactNode>(options: UseFieldOptions<Value, TError>): UseFieldReturnType<Value, TError>
```

## How it actually works: a one-field form in disguise

```typescript
type FieldValues = { field: Value };

const storeOptions: UseFormOptions<FieldValues, FieldValues, TError> = {
  mode,
  initialValues: { field: initialValue },
  validateInputOnChange: validateOnChange,
  validateInputOnBlur: validateOnBlur,
  ...(validateFn !== undefined ? { validate: { field: (v) => validateFn(v) } } : {}),
};

const storeRef = useRef<FormStoreApi<FieldValues, FieldValues, TError> | null>(null);
if (storeRef.current === null) {
  storeRef.current = createFormStore<FieldValues, FieldValues, TError>(storeOptions);
}
```

`useField` doesn't reimplement any form logic — it builds a real [createFormStore](../forms/store/01-create-form-store) instance whose `Values` type is the single-key object `{ field: Value }`, then exposes a narrower, field-shaped API over that one-field store. This is why `useField` gets validation debouncing, async validation generation-guarding, dirty/touched tracking, and the uncontrolled remount trick *for free* — it's all the exact same machinery [useForm](./01-use-form) uses, just pre-wired to operate on the single synthetic `'field'` path.

```typescript
const snapshot = useSyncExternalStore(
  useCallback((cb) => store.subscribe(cb), [store]),
  () => store.getSnapshot(),
  () => store.getServerSnapshot(),
);

const error = (snapshot.errors['field'] ?? null) as TError | null;
const isValidating = snapshot.fieldValidating['field'] === true;
const isDirty = store.isDirty('field');
const isTouched = store.isTouched('field');
const fieldKey = `${snapshot.formKey}-field-${snapshot.fieldKeys['field'] ?? 0}`;
```

Same `useSyncExternalStore` bridging pattern as [useForm](./01-use-form) — every reactive value is read off the snapshot for the `'field'` path specifically.

## `UseFieldOptions<Value, TError>`

| Option | Type | Default | Description |
|--------|------|---------|--------------|
| `initialValue` | `Value` | *(required)* | The field's starting value — becomes `{ field: initialValue }` internally. |
| `validate` | `(value: Value) => TError \| null \| undefined \| Promise<...>` | none | A single-field rule — note the signature takes only `value` (no `values`/`path`, unlike core's `ValidationRule`), since there's no meaningful "whole form" or "other fields" in a standalone field. |
| `validateOnChange` / `validateOnBlur` | `boolean` | `false` | Maps directly to the underlying store's `validateInputOnChange`/`validateInputOnBlur`. |
| `resolveValidationError` | `(error: unknown) => TError` | none | Same semantics as [UseFormOptions](../forms/types/01-store-types)'s option of the same name. |
| `type` | `'input' \| 'checkbox' \| 'radio'` | `'input'` | Forwarded to the internal `getInputProps('field', { type })` call. |
| `mode` | `FormMode` | `'controlled'` | **Note:** unlike [useForm](./01-use-form), `useField` does **not** override this to `'uncontrolled'` — it keeps core's own default. Pass `mode: 'uncontrolled'` explicitly if you want the same zero-re-render-on-typing behavior `useForm` gives you by default. |

## `UseFieldReturnType<Value, TError>`

| Property | Description |
|----------|--------------|
| `key` | Stable remount key — same purpose as `form.key(path)`, pre-resolved for the single field. |
| `getValue()` / `setValue(value \| updater)` | Read/write the field's value directly, bypassing `getInputProps` (useful for non-DOM-event-driven updates). |
| `reset()` | Resets to `initialValue`, clearing error/touched/dirty for this field. |
| `getInputProps()` | Returns the same shape as `form.getInputProps(path, { type })` would, with no arguments needed since there's only one field. |
| `error` | `TError \| null` — read directly, not a method. |
| `validate()` | Returns a `Promise` (always, regardless of whether the underlying rule is sync) resolving to the error or `null`/`undefined`. |
| `isValidating` / `isDirty` / `isTouched` | Booleans, read directly. |
| `setError(error)` / `clearError()` | Manual error control, equivalent to `form.setFieldError`/`clearFieldError` scoped to this field. |

## Basic usage

```tsx
import { useField } from '@headlesskit/forms-react';

function EmailInput() {
  const field = useField({
    initialValue: '',
    validate: (value) => (/^\S+@\S+\.\S+$/.test(value) ? null : 'Invalid email'),
    validateOnChange: true,
  });

  return (
    <div>
      <input key={field.key} {...field.getInputProps()} type="email" placeholder="Email" />
      {field.error && <span style={{ color: 'red' }}>{field.error}</span>}
    </div>
  );
}
```

## Advanced: a reusable validated-input component built entirely on `useField`

```tsx
function ValidatedInput({ label, initialValue, validate }: {
  label: string;
  initialValue: string;
  validate: (value: string) => string | null;
}) {
  const field = useField({ initialValue, validate, validateOnBlur: true, mode: 'uncontrolled' });
  return (
    <label>
      {label}
      <input key={field.key} {...field.getInputProps()} />
      {field.isTouched && field.error && <span>{field.error}</span>}
    </label>
  );
}
```

This component has zero awareness of any enclosing form — it's entirely self-contained, which is exactly the use case `useField` targets: composable, independently-testable field components.

## Common pitfalls

- **`useField`'s `mode` defaults to `'controlled'`, unlike `useForm`'s `'uncontrolled'` default** — if you want the same typing-performance benefit `useForm` gives you out of the box, you must explicitly pass `mode: 'uncontrolled'` to `useField`.
- **A `useField` instance is entirely independent of any `useForm` instance** — there's no automatic way to compose a `useField`-managed value into a larger form's `values`; if you need both a full form *and* an independently-validated standalone field's value, you'll need to manually bridge them (e.g. via `form.watch`/`form.setFieldValue` and the field's own `getValue`/`setValue`), since they're backed by two entirely separate store instances.
- **`options` is read only once**, exactly like [useForm](./01-use-form) — changing `initialValue`/`validate` on a later render has no effect on the already-created internal store.
