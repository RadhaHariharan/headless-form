# State Management Simplify

`@headlesskit/state-management-simplify` is a small, fast, bare-bones vanilla (framework-agnostic) store core and middleware set, with no boilerplate.

| Package | Description |
|---------|-------------|
| `@headlesskit/state-management` | Predictable, action/reducer-based store |
| `@headlesskit/state-management-simplify` | A small, fast, bare-bones store with no boilerplate |

---

## Installation

```bash
pnpm add @headlesskit/state-management-simplify
# or
npm install @headlesskit/state-management-simplify
```

`immer` is an **optional peer dependency**, needed only if you use the [`immer` middleware](10-middleware-immer):

```bash
pnpm add immer
```

## Core concepts

Where `@headlesskit/state-management` is built around dispatching plain-object actions through pure reducers, this package takes the opposite, more minimal approach:

1. **One function, no boilerplate.** `createStore` takes a single initializer function `(set, get, api) => state` and returns a store. There are no action types, no switch statements, no reducers required.
2. **`set` does a shallow merge by default.** Calling `set(partial)` merges `partial` into the current state with `Object.assign`. Pass `true` as the second argument to replace the state outright instead of merging.
3. **Middleware wraps the initializer, not the store.** Every middleware in this package (`reducerMiddleware`, `devtools`, `persist`, `immer`, `combine`, `subscribeWithSelector`, `unstable_ssrSafe`) has the same shape: it receives your `StateCreator` and returns a new, wrapped `StateCreator`. They compose by nesting function calls.

```
createStore(middlewareA(middlewareB(initializer))) → StoreApi<T>
```

This page covers concepts and how the pieces fit together. Each export below has its own dedicated page in the sidebar with full parameter tables, real source-grounded behavior, and basic + advanced examples:

- [createStore](02-create-store) — builds the store; covers `StoreApi`, `StateCreator`, `ExtractState`, `Mutate`
- [shallow](03-shallow) — the shallow-equality comparator used for selector-based re-render checks
- [combine](04-middleware-combine) — merges an initial state object into a `StateCreator`'s return value
- [reducerMiddleware](05-middleware-reducer) — `dispatch`/reducer pattern layered on top of a vanilla store
- [devtools](06-middleware-devtools) — in-app DevTools overlay integration
- [persist](07-middleware-persist) — persistence to `localStorage` (or any custom storage), with versioned migration
- [subscribeWithSelector](08-middleware-subscribe-with-selector) — selector-scoped subscriptions with an equality function
- [unstable_ssrSafe](09-middleware-ssr-safe) — guards against calling `setState` during server-side rendering
- [immer](10-middleware-immer) — write mutable-looking updates that produce immutable state via Immer

## A complete mental model, end to end

```typescript
import { createStore } from '@headlesskit/state-management-simplify';

type CounterState = {
  count: number;
  increment: () => void;
  decrement: () => void;
};

const store = createStore<CounterState>((set, get) => ({
  count: 0,
  increment: () => set((state) => ({ count: state.count + 1 })),
  decrement: () => set((state) => ({ count: state.count - 1 })),
}));

store.subscribe((state, prevState) => {
  console.log('count changed from', prevState.count, 'to', state.count);
});

store.getState().increment();
// logs: "count changed from 0 to 1"

console.log(store.getState().count); // 1
```

## When to reach for `state-management` instead

This package's `createStore` is a single, ungoverned function call — there's no enforced separation between "actions" and "state changes," and any function defined on the state object can call `set` directly. That's the appeal (less ceremony, smaller surface area) but it also means there's no built-in action log, no time-travel debugging without the `devtools` middleware, and no `combineReducers`-style enforced modularity. Reach for `@headlesskit/state-management` instead when you want predictable, traceable state changes (every change is an inspectable action object) or you're integrating with existing action/reducer-based tooling; reach for this package when you want the smallest possible API surface for typical app or component state.
