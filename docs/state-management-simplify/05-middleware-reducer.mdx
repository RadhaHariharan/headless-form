# reducerMiddleware

A middleware that layers a `dispatch(action)` / `(state, action) => state` reducer pattern on top of a vanilla store, while keeping the rest of the store's `setState`/`getState`/`subscribe` API intact. This is the bridge that lets the [`devtools`](06-middleware-devtools) middleware drive your store via `dispatchFromDevtools`.

```typescript
import { reducerMiddleware } from '@headlesskit/state-management-simplify';
```

## Signature

```typescript
reducerMiddleware<T, A extends { type: string }>(
  reducer: (state: T, action: A) => T,
  initialState: T,
): StateCreator<T & { dispatch: (a: A) => A }, [], [['headlesskit/reducer', A]]>
```

| Parameter | Type | Required | Description |
|-----------|------|----------|-------------|
| `reducer` | `(state: T, action: A) => T` | Yes | A pure reducer — given the current state and an action, returns the next state. |
| `initialState` | `T` | Yes | The store's initial state value. |

**Returns:** a `StateCreator` whose resulting store state is `initialState`'s shape plus a `dispatch` method, and which is type-tagged with the `'headlesskit/reducer'` mutator (consumed by `devtools` and other middleware that need to know `dispatch`/`dispatchFromDevtools` exist).

`reducerMiddleware` does **not** accept a separate `StateCreator` function the way `combine` does — you give it a reducer function and an initial state directly, and it builds the `StateCreator` for you.

## What it actually does

```typescript
const reducerMiddlewareImpl: ReducerMiddlewareImpl = (reducer, initial) => (set, _get, api) => {
  ;(api as any).dispatch = (action) => {
    ;(set as NamedSet<S>)((state) => reducer(state, action), false, action)
    return action
  }
  ;(api as any).dispatchFromDevtools = true

  return { dispatch: (...args) => (api as any).dispatch(...args), ...initial }
}
```

Two things happen:

1. **`api.dispatch` is installed directly on the store object** (not just returned in the state), and `api.dispatchFromDevtools = true` is set — this flag is what the `devtools` middleware checks (via `shouldDispatchFromDevtools`) to decide whether it should forward DevTools-originated actions into your store via `dispatch` instead of (or in addition to) `setState`.
2. **`dispatch` calls `set` with the reducer wrapped as a functional updater**, and crucially passes the **action itself as the third argument to `set`** — `set((state) => reducer(state, action), false, action)`. That third argument is exactly what the `devtools` middleware's wrapped `setState` reads as the action's `type` label for the DevTools timeline, so the action you dispatch shows up with its real `type` in the DevTools overlay, not a generic "anonymous" label.

The returned state object exposes a `dispatch` that just forwards to `api.dispatch`, so calling `store.getState().dispatch(action)` and `store.dispatch === api.dispatch` behave the same way (both routes go through `api.dispatch`).

## Basic usage

```typescript
import { createStore } from '@headlesskit/state-management-simplify';
import { reducerMiddleware } from '@headlesskit/state-management-simplify';

type CounterState = { count: number };
type CounterAction = { type: 'increment' } | { type: 'decrement' } | { type: 'reset' };

function counterReducer(state: CounterState, action: CounterAction): CounterState {
  switch (action.type) {
    case 'increment': return { count: state.count + 1 };
    case 'decrement': return { count: state.count - 1 };
    case 'reset': return { count: 0 };
    default: return state;
  }
}

const store = createStore(reducerMiddleware(counterReducer, { count: 0 }));

store.getState().dispatch({ type: 'increment' });
console.log(store.getState().count); // 1
```

## Advanced: combining reducerMiddleware with devtools for full DevTools dispatch support

Wrapping `reducerMiddleware` with `devtools` gives you the classic DevTools experience — every dispatched action appears in the timeline labeled by its `type`, and actions dispatched *from* the DevTools UI (e.g. clicking "Jump to action," or manually firing an action in the DevTools overlay) are routed back into your reducer through `dispatch`, because `devtools` detects `dispatchFromDevtools === true` and calls `api.dispatch(action)` for any non-`__setState` message:

```typescript
import { createStore } from '@headlesskit/state-management-simplify';
import { reducerMiddleware, devtools } from '@headlesskit/state-management-simplify';

type TodoState = { todos: string[] };
type TodoAction =
  | { type: 'todos/add'; payload: string }
  | { type: 'todos/clear' };

function todosReducer(state: TodoState, action: TodoAction): TodoState {
  switch (action.type) {
    case 'todos/add': return { todos: [...state.todos, action.payload] };
    case 'todos/clear': return { todos: [] };
    default: return state;
  }
}

const store = createStore(
  devtools(reducerMiddleware(todosReducer, { todos: [] }), { name: 'TodoStore' }),
);

store.getState().dispatch({ type: 'todos/add', payload: 'Buy milk' });
// The DevTools overlay timeline shows an action labeled "todos/add"
```

Note the ordering: `devtools` must wrap `reducerMiddleware` (not the other way around) so that `devtools` sees the `dispatch`/`dispatchFromDevtools` that `reducerMiddleware` installs on `api` when `devtools` runs its own initializer call — `devtoolsImpl` checks `shouldDispatchFromDevtools(api)` *after* calling `fn(api.setState, get, api)`, where `fn` here is the `reducerMiddleware`-wrapped initializer that sets `api.dispatchFromDevtools = true` as a side effect of running.

## Common pitfalls

- **Dispatching from inside the reducer.** Unlike `@headlesskit/state-management`'s `createStore`, this `reducerMiddleware` does not guard against calling `dispatch` while the reducer is executing — there's no "Reducers may not dispatch actions" check here. Keep reducers pure by convention; the middleware won't enforce it for you.
- **Forgetting the action becomes the DevTools label.** The third argument to the underlying `set` call is the raw action object, not just its `type` string — if you rely on `devtools`'s "anonymous" fallback labeling logic elsewhere in the same store, dispatched-via-`reducerMiddleware` actions will instead show their actual action object/type, which is usually what you want but can be surprising if you expected uniform anonymous-looking entries.
- **Returning `undefined` from the reducer for unhandled actions.** If your `default` case doesn't `return state`, the store's state becomes `undefined` after any unrecognized action.
