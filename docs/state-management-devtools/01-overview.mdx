# State Management Devtools

`@headlesskit/state-management-devtools` is a full time-travel dev-tools connector for headlesskit state-management stores. It records the complete action history in memory, computes state at any point in that history (a "lifted store", the same technique real Redux DevTools time-travel is built on), and exposes it (plus a small bit of dock-panel UI state) to whatever UI you render on top of it — most commonly [`@headlesskit/state-management-devtools-react`](../state-management-devtools-react/01-overview.mdx).

```bash
pnpm add @headlesskit/state-management-devtools
# or
npm install @headlesskit/state-management-devtools
```

This package is framework-agnostic and renders nothing itself — it's the connector + the lifted-state engine, not the UI.

---

## Why this package exists

Both of headlesskit's state-management packages already have a "connector" seam built in, but neither ships an implementation:

- `@headlesskit/state-management-toolkit`'s `configureStore` calls `composeWithDevTools(...)`, which reads `window.__HEADLESSKIT_DEVTOOLS_EXTENSION_COMPOSE__` — see [devtoolsExtension](../state-management-toolkit/15-devtools-extension.mdx).
- `@headlesskit/state-management-simplify`'s `devtools` middleware reads `window.__HEADLESSKIT_DEVTOOLS_EXTENSION__` and calls `.connect(options)` — see [middleware/devtools](../state-management-simplify/06-middleware-devtools.mdx).

`installDevtools()` from this package *is* that connector — it populates both globals with implementations backed by the same in-memory, time-travel-capable history, so a `configureStore`-based store and a `state-management-simplify` store can show up side by side in one inspector.

---

## Two replay strategies, one engine

Real time-travel means more than recording a log — it means being able to recompute "what would the state be if action #3 never happened," and have the *live* store reflect that. The mechanism differs by store shape, but both share the same lifted-state model (see [lifted-state](./06-lifted-state.mdx)):

- **Reducer-based stores** (`configureStore`): the connector's enhancer reads the real reducer and "lifts" the store — every dispatch is replayed through the actual reducer to compute `computedStates`, so jumping/skipping/sweeping changes what `store.getState()` returns *and* notifies subscribers, exactly like a normal dispatch would.
- **Zustand-style stores** (`state-management-simplify`'s `devtools` middleware): there's no reducer to call, only a `set(partial)` API. The connector derives a shallow key-level **patch** from each recorded state transition, and replays patches instead of actions. Skip/jump/sweep results are pushed back into the live store through that middleware's existing `connection.subscribe()` handler (it already implements `JUMP_TO_STATE`/`RESET`/`COMMIT`/`ROLLBACK`/`PAUSE_RECORDING` — the connector just had nothing driving it before this package existed).

## Quick start

Call `installDevtools()` once, **before** any store is created — `configureStore`/`devtools(...)` read the connector globals at store-creation time, so installing the connector afterward means that store never connects.

```typescript
// devtools-setup.ts
import { installDevtools } from '@headlesskit/state-management-devtools';

export const { inspectorStore, dockStore } = installDevtools();
```

```typescript
// store.ts
import './devtools-setup'; // side-effecting import, must run first
import { configureStore } from '@headlesskit/state-management-toolkit';
import rootReducer from './root-reducer';

export const store = configureStore({ reducer: rootReducer });
// every store.dispatch(...) is now part of a time-travel-capable history
```

```typescript
// a state-management-simplify store connects to the same inspector
import { create } from '@headlesskit/state-management-simplify';
import { devtools } from '@headlesskit/state-management-simplify';

export const useCounterStore = create(
  devtools((set) => ({ count: 0, increment: () => set((s) => ({ count: s.count + 1 })) }), {
    name: 'counter',
  }),
);
```

Render the result with [`<DevtoolsPanel inspectorStore={inspectorStore} dockStore={dockStore} />`](../state-management-devtools-react/01-overview.mdx), or read `inspectorStore.getSnapshot()` / `dockStore.getSnapshot()` directly to build a custom UI.

## The connector contract

`installDevtools` assigns two globals, matching exactly what the two consuming packages already look for:

| Global | Read by | Shape |
|--------|---------|-------|
| `window.__HEADLESSKIT_DEVTOOLS_EXTENSION__` | `state-management-simplify`'s `devtools` middleware | `{ (config?) => enhancer; connect(config) => { init, send, subscribe, unsubscribe } }` |
| `window.__HEADLESSKIT_DEVTOOLS_EXTENSION_COMPOSE__` | `state-management-toolkit`'s `composeWithDevTools` | `(config) => (...enhancers) => enhancer`, or called directly with enhancers |

Both ultimately call the same underlying connector logic (`createDevtoolsExtension`), so a store connected through either global lands its history in the same `InspectorStore`, keyed by connection name (the `name` option each package's devtools config already accepts).

## Common pitfalls

- **Install before creating any store.** This is the single most common setup mistake — if a store is created before `installDevtools()` runs, that store captured `undefined` for the connector globals and will never connect, even after you install the connector later.
- **`state-management-simplify` time-travel is patch-based, not reducer-based.** See [Two replay strategies](#two-replay-strategies-one-engine) — skipping an action that expressed a *relative* update (`count: prev.count + 1`) won't undo correctly the way a real reducer replay would, since the connector only has the resulting patch, not the update logic.
- **History is in-memory and capped.** It resets on every page reload, and each connection keeps at most `maxActionsPerConnection` staged actions (default 200) — past the cap, the oldest actions are folded into the committed baseline (not dropped), so the current state stays correct even though the oldest individual actions are no longer inspectable.
- **On the server, `installDevtools()` is a safe no-op** that still returns usable (empty) stores — it only touches `window` when `window` exists.
