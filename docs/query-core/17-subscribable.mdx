# Subscribable

**File:** `src/subscribable.ts`

`Subscribable` is the base class behind every pub/sub object in `@headlesskit/query-core` — `FocusManager`, `OnlineManager`, `QueryCache`, `MutationCache`, `QueryObserver`, `MutationObserver`, and `QueriesObserver` all extend it. It is not normally imported directly by application code; you interact with it indirectly through `focusManager.subscribe(...)`, `observer.subscribe(...)`, etc. You'd only import it yourself if building a custom observer-like class.

```typescript
import { Subscribable } from '@headlesskit/query-core';
```

## Signature

```typescript
class Subscribable<TListener extends Function> {
  protected listeners: Set<TListener>;
  subscribe(listener: TListener): () => void;
  hasListeners(): boolean;
  protected onSubscribe(): void;
  protected onUnsubscribe(): void;
}
```

| Member | Type | Description |
|--------|------|--------------|
| `listeners` | `Set<TListener>` (protected) | Backing store of all currently-subscribed listener functions |
| `subscribe(listener)` | `(listener: TListener) => () => void` | Adds a listener, calls `onSubscribe()`, returns an unsubscribe function |
| `hasListeners()` | `() => boolean` | `true` if `listeners.size > 0` |
| `onSubscribe()` | `protected` hook | No-op by default — override to run setup logic on first/any subscribe |
| `onUnsubscribe()` | `protected` hook | No-op by default — override to run teardown logic on unsubscribe |

## Basic usage

`Subscribable` is generic over the listener function's signature (`TListener extends Function`). Subclass it and call `super()` in your constructor:

```typescript
import { Subscribable } from '@headlesskit/query-core';

type CounterListener = (count: number) => void;

class CounterEmitter extends Subscribable<CounterListener> {
  #count = 0;

  increment() {
    this.#count++;
    this.listeners.forEach((listener) => listener(this.#count));
  }
}

const emitter = new CounterEmitter();
const unsubscribe = emitter.subscribe((count) => console.log('count is', count));

emitter.increment(); // logs "count is 1"
unsubscribe();
emitter.increment(); // no log — listener was removed
```

## Advanced: lazy setup/teardown via onSubscribe/onUnsubscribe

The real value of `Subscribable` is the `onSubscribe`/`onUnsubscribe` hooks, which let a subclass lazily attach to an external resource (a DOM event, a native module) only while it actually has listeners — exactly how [FocusManager](./14-focus-manager) and [OnlineManager](./15-online-manager) work internally:

```typescript
class VisibilityTracker extends Subscribable<(visible: boolean) => void> {
  #cleanup?: () => void;

  protected onSubscribe(): void {
    if (!this.#cleanup) {
      const handler = () => {
        this.listeners.forEach((l) => l(document.visibilityState === 'visible'));
      };
      document.addEventListener('visibilitychange', handler);
      this.#cleanup = () => document.removeEventListener('visibilitychange', handler);
    }
  }

  protected onUnsubscribe(): void {
    // Only tear down once the LAST listener leaves
    if (!this.hasListeners()) {
      this.#cleanup?.();
      this.#cleanup = undefined;
    }
  }
}
```

This is the exact pattern `FocusManager` and `OnlineManager` use: `onSubscribe` calls `this.setEventListener(this.#setup)` if no cleanup function exists yet, and `onUnsubscribe` checks `if (!this.hasListeners())` before tearing down — so the underlying `window.addEventListener('visibilitychange', ...)` (or `'online'`/`'offline'`) is only attached once, no matter how many separate `subscribe()` calls come in, and only detached once every subscriber has unsubscribed.

## Method-by-method breakdown

### Constructor

```typescript
constructor() {
  this.subscribe = this.subscribe.bind(this)
}
```

Binds `subscribe` to the instance in the constructor. This means `subscribe` can be safely destructured or passed as a bare reference (`const { subscribe } = focusManager`) without losing its `this` context — useful when wiring it directly into a framework adapter's effect/lifecycle hook.

### `subscribe(listener)`

```typescript
subscribe(listener: TListener): () => void {
  this.listeners.add(listener)
  this.onSubscribe()
  return () => {
    this.listeners.delete(listener)
    this.onUnsubscribe()
  }
}
```

Adds `listener` to the `listeners` `Set` (so subscribing the *same* function reference twice is a no-op — `Set` semantics), then unconditionally calls `onSubscribe()` — every subscribe call triggers it, not just the first. The returned cleanup function deletes the listener and calls `onUnsubscribe()` — again, every unsubscribe call triggers it. It's the *subclass's* responsibility to make `onSubscribe`/`onUnsubscribe` idempotent (e.g. guarding with `hasListeners()`), as shown above.

### `hasListeners()`

```typescript
hasListeners(): boolean {
  return this.listeners.size > 0
}
```

A simple `size > 0` check on the `Set`. Used by subclasses inside `onUnsubscribe` to detect the "last listener just left" transition.

### `onSubscribe()` / `onUnsubscribe()`

Both are `protected` and no-ops by default (`// Do nothing`). They exist purely as override points — `Subscribable` itself never calls into any side effects.

## Common pitfalls

- **Forgetting to call `super()`.** Since the constructor binds `this.subscribe`, a subclass constructor that skips `super()` (impossible in TypeScript/JS without erroring) or that overrides `subscribe` directly will lose this binding — prefer overriding `onSubscribe`/`onUnsubscribe` instead of `subscribe` itself.
- **Assuming `onSubscribe`/`onUnsubscribe` only fire once.** They fire on *every* subscribe/unsubscribe call, not just the first/last. Guard your setup/teardown logic with `hasListeners()` (or an internal cleanup-ref check) the way `FocusManager`/`OnlineManager` do, or you'll attach duplicate event listeners.
- **Iterating `listeners` and mutating it in the same pass.** `subscribe`/`unsubscribe` calls inside a listener callback mutate the same `Set` you may be iterating — copy to an array first if your subclass notifies listeners by iterating directly (query-core's higher-level classes route through `notifyManager` to avoid this).
