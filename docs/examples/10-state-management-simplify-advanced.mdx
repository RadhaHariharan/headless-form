# State Management Simplify — Advanced Examples

Fifty examples covering architecture-level concerns: full middleware stacks, SSR, testing, store factories, and performance. Assumes you've read [Basic](./08-state-management-simplify-basic.mdx) and [Medium](./09-state-management-simplify-medium.mdx).

---

## 1. The full middleware stack composed together

```typescript
import { createStore, devtools, persist, subscribeWithSelector, createJSONStorage } from '@headlesskit/state-management-simplify';

const useStore = create<Store>()(
  devtools(
    persist(
      subscribeWithSelector((set) => ({ count: 0, increment: () => set((s) => ({ count: s.count + 1 })) })),
      { name: 'store', storage: createJSONStorage(() => sessionStorage) },
    ),
    { name: 'MyStore' },
  ),
);
```

**How it works:** middleware here composes by literal function nesting, innermost-first — `subscribeWithSelector` wraps your raw initializer, `persist` wraps *that*, and `devtools` wraps the result of `persist`. Each layer only modifies the `set`/`get`/store API the layer inside it receives; `devtools`, being outermost, is the one whose recorded actions the browser's Redux DevTools extension ultimately sees, after `persist`'s and `subscribeWithSelector`'s own internal bookkeeping has already run for that update.

## 2. The `immer` middleware for ergonomic nested updates

```typescript
import { immer } from '@headlesskit/state-management-simplify';

const useStore = create<{ todos: Todo[] }>()(
  immer((set) => ({
    todos: [],
    toggle: (id: string) =>
      set((state) => {
        const todo = state.todos.find((t) => t.id === id);
        if (todo) todo.done = !todo.done; // looks like a mutation...
      }),
  })),
);
```

**How it works:** `immer` wraps `set` so that the function you pass to it can "mutate" a draft proxy directly (`todo.done = !todo.done`) instead of manually spreading every level of nesting (`{...state, todos: state.todos.map(...)}`) — Immer itself produces the real, structurally-shared immutable update underneath. This solves exactly the shallow-merge nesting gotcha from [Basic #7](./08-state-management-simplify-basic.mdx#7-a-shallow-merge-gotcha-with-nested-objects), generalized to arbitrarily deep state.

## 3. An SSR-safe store

```typescript
import { unstable_ssrSafe } from '@headlesskit/state-management-simplify';

const useStore = create<Store>()(unstable_ssrSafe((set) => ({ count: 0 })));
```

**How it works:** a store created once at module scope is normally *shared* across every request on the server — fine for a stateless server, but a correctness bug for SSR frameworks that reuse the same Node.js process across multiple concurrent requests, where one user's state could leak into another's render. `unstable_ssrSafe` changes the store's lifecycle so each render gets its own isolated state instead of one shared module-level instance; reach for it specifically when you see cross-request state bleed in an SSR environment, not as a default.

## 4. A guided time-travel debugging session using a manually-kept array of snapshots

```typescript
const history: { count: number }[] = [];
useStore.subscribe((state) => history.push({ count: state.count }));

// 1. Dispatch a few actions through the live store.
useStore.getState().increment(); // count: 1, history: [{ count: 1 }]
useStore.getState().increment(); // count: 2, history: [{ count: 1 }, { count: 2 }]
useStore.getState().increment(); // count: 3, history: [{ count: 1 }, { count: 2 }, { count: 3 }]

// 2. "Skip" the middle entry by filtering it out of the recorded history...
const withoutMiddleEntry = [history[0], history[2]];
// 3. ...then "jump back" by re-applying the last remaining snapshot directly.
useStore.setState(withoutMiddleEntry[withoutMiddleEntry.length - 1]);
useStore.getState().count; // 3 — re-applying a snapshot restores an ABSOLUTE value, not a recomputed one
```

**How it works:** `history` records the *resulting* state object after every `set` call, exactly like a patch-based devtools history would — there's no reducer here to re-run, so "jumping back" can only ever mean re-applying one of these recorded absolute snapshots via `setState`, never recomputing what should have happened. That's the same limitation [Example 17](#17-time-travel-replays-patch-based-limitation-on-nested-relative-updates) walks through in more depth: skipping an entry out of a snapshot history and reapplying what's left is exact only when each recorded value doesn't depend on values skipped before it, which is true for this additive counter but breaks for relative updates like "double the current value."

## 5. Writing your own middleware

```typescript
type Logger = <T>(f: StateCreator<T>, name?: string) => StateCreator<T>;

const logger: Logger = (f, name) => (set, get, store) => {
  const loggedSet: typeof set = (...args) => {
    set(...args);
    console.log(`${name ?? 'store'} updated:`, get());
  };
  return f(loggedSet, get, store);
};

const useStore = create<Store>()(logger((set) => ({ count: 0 }), 'counter'));
```

**How it works:** a middleware is a function that takes a `StateCreator` and returns another `StateCreator` — its whole job is to intercept the `set`/`get`/`store` triple before handing a (possibly wrapped) version to the real initializer `f`. Here, `loggedSet` calls the real `set` first, then logs — wrapping in the other order (log, then call `set`) would log the *previous* state instead of the one just written.

## 6. Unit-testing a store with no React at all

```typescript
import { createStore } from '@headlesskit/state-management-simplify';

test('increment increases count by one', () => {
  const store = createStore<{ count: number; increment: () => void }>((set) => ({
    count: 0,
    increment: () => set((s) => ({ count: s.count + 1 })),
  }));

  store.getState().increment();
  expect(store.getState().count).toBe(1);
});
```

**How it works:** the vanilla `createStore` (from `@headlesskit/state-management-simplify`, not the `-react` package's `create`) is the exact same store the React hook wraps — testing against it directly needs no `render()`, no `act()`, and no DOM, exercising the real store logic your component will eventually use.

## 7. A store factory for multiple independent instances

```typescript
function createTabStore(tabId: string) {
  return create<{ scrollPosition: number; setScroll: (n: number) => void }>((set) => ({
    scrollPosition: 0,
    setScroll: (scrollPosition) => set({ scrollPosition }),
  }));
}

const stores = new Map<string, ReturnType<typeof createTabStore>>();
function getTabStore(tabId: string) {
  if (!stores.has(tabId)) stores.set(tabId, createTabStore(tabId));
  return stores.get(tabId)!;
}
```

**How it works:** `create`/`createStore` are just functions you can call as many times as you want — there's no requirement (or built-in support) for a single global singleton, so a "store per tab/per-tenant/per-document-id" architecture is just a factory function plus your own registry (a `Map`, here) keyed however your domain needs.

## 8. Memoizing an expensive derived selector

```typescript
import { useMemo } from 'react';

function ExpensiveList() {
  const items = useStore((state) => state.items);
  const sorted = useMemo(() => [...items].sort(expensiveComparator), [items]);
  return <ul>{sorted.map((item) => <li key={item.id}>{item.name}</li>)}</ul>;
}
```

**How it works:** the store's own selector mechanism (`Object.is`/`useShallow`) only controls *whether the component re-renders* — it does nothing to prevent expensive work from re-running *inside* a render that does happen. Wrapping the actual sort in `useMemo`, keyed on the same `items` reference the selector already returns, skips recomputing the sort on renders triggered by *other* state changes (anything not `items`) while still recomputing it correctly when `items` itself changes.

## 9. Optimistic updates with subscribe-based error recovery

```typescript
const useCartStore = create<{ items: Item[]; removeOptimistic: (id: string) => void }>((set, get) => ({
  items: [],
  removeOptimistic: (id) => {
    const before = get().items;
    set({ items: before.filter((i) => i.id !== id) });
    api.removeItem(id).catch(() => set({ items: before })); // restore the captured snapshot
  },
}));
```

**How it works:** capturing `get().items` *before* the optimistic `set` (rather than trying to reconstruct what was removed afterward) gives the `.catch` rollback an exact, trivially correct snapshot to restore — the same technique as the [state-management package's optimistic-update example](./07-state-management-advanced.mdx#7-manual-optimistic-updates-with-rollback-middleware), just expressed as a closure variable instead of a middleware.

## 10. Migrating a Redux-style reducer into a simplify store

```typescript
import { reducerMiddleware } from '@headlesskit/state-management-simplify';

function counterReducer(state: { count: number }, action: { type: string }) {
  switch (action.type) {
    case 'increment': return { count: state.count + 1 };
    default: return state;
  }
}

const useStore = create<{ count: number; dispatch: (action: { type: string }) => void }>()(
  reducerMiddleware(counterReducer, { count: 0 }),
);

useStore.getState().dispatch({ type: 'increment' });
```

**How it works:** `reducerMiddleware` is an adapter, not a rewrite — it keeps your existing pure `(state, action) => state` reducer completely unchanged and exposes a `dispatch` action on the resulting store that internally calls `set(reducer(get(), action))`. This is the path of least resistance for porting an existing `@headlesskit/state-management` (or Redux) reducer into this package's store shape without touching its logic at all.

## 11. A typed helper to reduce store-creation boilerplate

```typescript
function createBoundedStore<T extends object>(initializer: StateCreator<T>, name: string) {
  return create<T>()(devtools(persist(initializer, { name }), { name }));
}

const useSettingsStore = createBoundedStore<SettingsStore>((set) => ({ theme: 'light' }), 'settings');
const useCartStore = createBoundedStore<CartStore>((set) => ({ items: [] }), 'cart');
```

**How it works:** once a codebase settles on "every store gets devtools + persist," wrapping that decision in one generic helper means each individual store's call site states only what's unique to it (its shape and a name) — the middleware stack itself lives in exactly one place, so changing it later (e.g. adding `subscribeWithSelector` everywhere) is a one-line change instead of a find-and-replace across every store file.

## 12. Comparing render counts: whole-state vs. selector vs. `useShallow`

```tsx
function renderCounter(label: string) {
  const count = useRef(0);
  count.current += 1;
  return <small>{label}: {count.current} renders</small>;
}

function WholeState() { useStore(); return renderCounter('whole-state'); }
function Selector() { useStore((s) => s.count); return renderCounter('selector'); }
function Shallow() { useStore(useShallow((s) => ({ count: s.count }))); return renderCounter('shallow'); }
```

**How it works:** dispatching an action that changes an *unrelated* field re-renders `WholeState` every time (it has no selector to filter on), leaves `Selector` untouched (its selected `count` value didn't change), and also leaves `Shallow` untouched (same reasoning, plus protection against the object-literal-identity issue from [Medium #9](./09-state-management-simplify-medium.mdx#9-useshallow-to-select-multiple-fields-at-once) if the selector returned more than one field). Running all three side by side against the same store and the same dispatched actions is the most direct way to *see* — not just read about — why selector-based subscriptions matter.

## 13. Three middleware composed on a deeply nested, multi-domain store

```typescript
import { createStore, devtools, persist, createJSONStorage } from '@headlesskit/state-management-simplify';
import { immer } from '@headlesskit/state-management-simplify';

interface AppStore {
  user: { profile: { name: string; email: string }; auth: { token: string | null } };
  cart: { items: { id: string; qty: number }[] };
  preferences: { theme: string; locale: string };
}

const useAppStore = create<AppStore>()(
  devtools(
    persist(
      immer((set) => ({
        user: { profile: { name: '', email: '' }, auth: { token: null } },
        cart: { items: [] },
        preferences: { theme: 'light', locale: 'en' },
      })),
      { name: 'app-store', storage: createJSONStorage(() => localStorage), partialize: (s) => ({ preferences: s.preferences }) },
    ),
    { name: 'AppStore' },
  ),
);

useAppStore.setState((state) => {
  state.cart.items.push({ id: 'sku1', qty: 1 }); // immer draft mutation, three layers in
});
```

**How it works:** composition is still innermost-first function nesting — `immer` wraps the raw initializer so the action body can mutate a `Draft` directly even though `user`/`cart`/`preferences` are three independent nested domains; `persist` wraps the immer-wrapped result, so what it persists (filtered by `partialize` to just `preferences`) is the *already-immer-produced* immutable state, not a draft; `devtools`, outermost, records the final committed state after both inner layers have run. Each middleware only ever sees the `set`/`get`/`api` triple the layer inside it hands up — `devtools` has no idea `immer` is even in the stack, it just sees ordinary `set` calls producing ordinary state diffs.

## 14. `unstable_ssrSafe`'s real mechanism: it throws, it doesn't isolate

```typescript
import { unstable_ssrSafe } from '@headlesskit/state-management-simplify';

const useStore = create<{ count: number }>()(
  unstable_ssrSafe((set) => ({ count: 0 /* no actions reference set at init time */ })),
);

// On the server (typeof window === 'undefined'):
useStore.setState({ count: 1 }); // throws: "Cannot set state of store in SSR"
```

**How it works:** contrary to a "gives each request its own state" intuition, `ssrSafe`'s actual implementation (`packages/state-management-simplify/src/middleware/ssrSafe.ts`) detects `typeof window === 'undefined'` and, only in that case, replaces `api.setState` with a function that unconditionally throws — the initializer still runs and produces real initial state for SSR'd markup to read via `getState()`, but any code path that calls `set` during server rendering fails loudly instead of silently mutating a module-level store that's shared across concurrent requests. This converts an easy-to-miss cross-request state leak into an immediate, debuggable crash during development.

## 15. A shopping cart with nested totals recomputed via immer drafts

```typescript
interface CartStore {
  cart: { items: { id: string; price: number; qty: number }[]; total: number };
  addItem: (id: string, price: number) => void;
  setQty: (id: string, qty: number) => void;
}

const useCartStore = create<CartStore>()(
  immer((set) => ({
    cart: { items: [], total: 0 },
    addItem: (id, price) =>
      set((state) => {
        state.cart.items.push({ id, price, qty: 1 });
        state.cart.total = state.cart.items.reduce((sum, i) => sum + i.price * i.qty, 0);
      }),
    setQty: (id, qty) =>
      set((state) => {
        const item = state.cart.items.find((i) => i.id === id);
        if (item) item.qty = qty;
        state.cart.total = state.cart.items.reduce((sum, i) => sum + i.price * i.qty, 0);
      }),
  })),
);
```

**How it works:** both actions push/mutate `state.cart.items` directly through the Immer draft and then recompute `state.cart.total` as a second mutation in the *same* draft — Immer batches every mutation made during one `produce` call into a single new immutable result, so even though this touches both `items` and `total` it still produces exactly one new `cart` object and triggers exactly one `set`. The equivalent plain-spread version would need to compute the new `items` array first, then build the new `cart` object referencing both the new `items` and the freshly computed `total` in one literal — Immer just defers that bookkeeping to the library.

## 16. A hand-built normalized entity cache (no entity adapter exists in this package)

```typescript
interface TodosStore {
  todos: { byId: Record<string, { id: string; text: string; done: boolean }>; allIds: string[] };
  addTodo: (text: string) => void;
  removeTodo: (id: string) => void;
}

const useTodosStore = create<TodosStore>((set) => ({
  todos: { byId: {}, allIds: [] },
  addTodo: (text) => {
    const id = crypto.randomUUID();
    set((state) => ({
      todos: {
        byId: { ...state.todos.byId, [id]: { id, text, done: false } },
        allIds: [...state.todos.allIds, id],
      },
    }));
  },
  removeTodo: (id) =>
    set((state) => {
      const { [id]: _removed, ...rest } = state.todos.byId;
      return { todos: { byId: rest, allIds: state.todos.allIds.filter((x) => x !== id) } };
    }),
}));
```

**How it works:** unlike Redux Toolkit's `createEntityAdapter`, this package ships no normalized-collection helper — `byId`/`allIds` is a convention you build by hand, and every action touching it has to keep both halves in sync manually (`addTodo` writes to both; `removeTodo` deletes from `byId` via destructuring-omission and filters `allIds`). The payoff over a plain array (as in [Basic #16](./08-state-management-simplify-basic.mdx#16-updating-one-item-inside-a-plain-array-field)) is O(1) lookup-by-id (`todos.byId[id]`) instead of an O(n) `.find`/`.map` scan, at the cost of this extra bookkeeping discipline on every write.

## 17. A manually-kept snapshot history's patch-based limitation on nested relative updates

```typescript
interface CounterStore {
  nested: { count: number };
  incrementByCurrentCount: () => void; // relative: doubles the count
}

const history: CounterStore['nested'][] = [];
useStore.subscribe((state) => history.push({ ...state.nested }));

useStore.getState().incrementByCurrentCount(); // nested.count: 1 -> 2, history: [{ count: 2 }]
useStore.getState().incrementByCurrentCount(); // nested.count: 2 -> 4, history: [{ count: 2 }, { count: 4 }]

// "Skip" the first recorded snapshot, keep only the second, then re-apply it:
useStore.setState({ nested: history[1] });
useStore.getState().nested.count; // 4, NOT 2 — re-applying a snapshot restores an absolute value
```

**How it works:** `history` records each step as the *resulting* `{ count: 2 }` then `{ count: 4 }` — absolute values, not "doubled the previous value," because a `subscribe` callback only ever sees what `state.nested` already became, never the operation that produced it. Skipping the first entry and re-applying only the second snapshot lands on whatever absolute value that snapshot held (`4`), not on what re-running `incrementByCurrentCount` against the post-skip state would have produced (`2`, doubling from `1`). This is the general case [Example 4](#4-a-guided-time-travel-debugging-session-using-a-manually-kept-array-of-snapshots) hints at: snapshot replay is exact only when a recorded value doesn't depend on values skipped before it, which a *relative* update like "double the current value" violates and an *additive* one (`count + 1`, as in Example 4's counter) does not.

## 18. Testing a nested-state store slice in isolation

```typescript
import { createStore } from '@headlesskit/state-management-simplify';

interface CartStore {
  cart: { items: { id: string; qty: number }[] };
  addItem: (id: string) => void;
}

function makeCartStore() {
  return createStore<CartStore>((set) => ({
    cart: { items: [] },
    addItem: (id) =>
      set((state) => ({ cart: { items: [...state.cart.items, { id, qty: 1 }] } })),
  }));
}

test('addItem appends without mutating the previous items array', () => {
  const store = makeCartStore();
  const before = store.getState().cart.items;
  store.getState().addItem('sku1');
  expect(store.getState().cart.items).not.toBe(before); // new array reference
  expect(before).toHaveLength(0);                        // original untouched
});
```

**How it works:** `makeCartStore` is a factory (same pattern as [Example 7](#7-a-store-factory-for-multiple-independent-instances)) so each test gets a fresh, isolated store instance instead of sharing module-level state across test files — and asserting `not.toBe` on the nested `items` array, alongside checking the captured `before` reference is unchanged, verifies the *immutability* property itself (a new array was produced, the old one wasn't mutated in place), not just the resulting content, which is the failure mode nested-update bugs most often introduce.

## 19. A store-factory pattern for per-tab nested state

```typescript
interface TabStore {
  tab: { scroll: { x: number; y: number }; filters: { query: string } };
  setScroll: (x: number, y: number) => void;
}

function createTabStore() {
  return create<TabStore>((set) => ({
    tab: { scroll: { x: 0, y: 0 }, filters: { query: '' } },
    setScroll: (x, y) => set((state) => ({ tab: { ...state.tab, scroll: { x, y } } })),
  }));
}

const tabStores = new Map<string, ReturnType<typeof createTabStore>>();
function useTabStore(tabId: string) {
  if (!tabStores.has(tabId)) tabStores.set(tabId, createTabStore());
  return tabStores.get(tabId)!;
}

function ScrollIndicator({ tabId }: { tabId: string }) {
  const useStore = useTabStore(tabId);
  const { x, y } = useStore((state) => state.tab.scroll);
  return <span>{x}, {y}</span>;
}
```

**How it works:** extending [Example 7](#7-a-store-factory-for-multiple-independent-instances)'s factory pattern to nested state changes nothing about the factory mechanics — `createTabStore()` still just returns a brand-new hook with its own closure over a brand-new vanilla store each call — but it does mean every nested field (`scroll`, `filters`) is independently isolated per tab too, so two `ScrollIndicator`s for different `tabId`s never share, race on, or leak updates into each other's `scroll` state, unlike a single store keyed by `tabId` inside one nested object would risk if an action forgot to scope its update correctly.

## 20. Render-count comparison: plain-spread vs. immer on a deep nested update

```tsx
function PlainSpreadList() {
  const items = usePlainStore((state) => state.board.columns[0].tasks);
  const renders = useRef(0); renders.current += 1;
  return <p>plain: {renders.current} ({items.length} tasks)</p>;
}

function ImmerList() {
  const items = useImmerStore((state) => state.board.columns[0].tasks);
  const renders = useRef(0); renders.current += 1;
  return <p>immer: {renders.current} ({items.length} tasks)</p>;
}

// Toggling a task in column[1] (not column[0]) on both stores:
usePlainStore.getState().toggleTask('c2', 't5');
useImmerStore.getState().toggleTask('c2', 't5');
```

**How it works:** both implementations re-render the same number of times here — neither produces a *correct*, reference-stable `columns[0]` when only `columns[1]` changed, because both `.map` over the full `columns` array (the plain version explicitly, immer's `produce` internally when any sibling element's container is touched at all only if your draft access pattern forces a copy). The actual lesson is the opposite of "immer reduces renders": immer's ergonomic win is fewer *lines of spread code*, not fewer renders — render counts are still governed entirely by whether the selector's returned reference changed, identical to [Example 12](#12-comparing-render-counts-whole-state-vs-selector-vs-useshallow)'s comparison, regardless of which middleware produced that reference.

## 21. A composite settings panel tying `persist` and `devtools` together

```typescript
interface SettingsStore {
  preferences: { theme: 'light' | 'dark'; fontSize: number; notifications: { email: boolean; push: boolean } };
  setTheme: (theme: 'light' | 'dark') => void;
  toggleEmailNotifications: () => void;
}

const useSettingsStore = create<SettingsStore>()(
  devtools(
    persist(
      (set) => ({
        preferences: { theme: 'light', fontSize: 14, notifications: { email: true, push: false } },
        setTheme: (theme) => set((state) => ({ preferences: { ...state.preferences, theme } }), false, 'setTheme'),
        toggleEmailNotifications: () =>
          set(
            (state) => ({
              preferences: {
                ...state.preferences,
                notifications: { ...state.preferences.notifications, email: !state.preferences.notifications.email },
              },
            }),
            false,
            'toggleEmailNotifications',
          ),
      }),
      { name: 'settings-panel', merge: (persisted, current) => ({ ...current, ...(persisted as object) }) },
    ),
    { name: 'SettingsPanel' },
  ),
);
```

**How it works:** the third argument to `set` (`'setTheme'`, `'toggleEmailNotifications'`) is `devtools`'s action-name parameter — without it, the Inspector would label every update from this store `anonymous` or whatever `findCallerName` manages to guess from the stack trace, but naming it explicitly makes the lifted-state history readable when several nested-preference actions fire close together. The explicit `merge` function here is the *default* behavior spelled out (`{ ...currentState, ...persistedState }`) but matters for documentation purposes: since `partialize` wasn't supplied, the entire `preferences` object — including the unpersisted-by-convention `notifications` sub-object — round-trips through storage as-is.

## 22. SSR hydration timing: `persist` resolves after first paint

```tsx
function ThemedRoot({ children }: { children: React.ReactNode }) {
  const hasHydrated = useSettingsStore.persist.hasHydrated();
  const theme = useSettingsStore((state) => state.preferences.theme);

  if (!hasHydrated) return <div data-theme="light">{children}</div>; // server default, always
  return <div data-theme={theme}>{children}</div>;
}
```

**How it works:** on the server, `persist`'s `hydrate()` either never runs (no `localStorage`) or the `storage` option itself throws inside `createJSONStorage`'s `try/catch`, returning `undefined` and leaving the initializer's plain defaults in place — so SSR-rendered markup always reflects `theme: 'light'`. On the client, hydration is asynchronous even when storage access itself is synchronous (the `Thenable` chain in `persist.ts` always resolves via `.then`), so there's a brief window after mount where `useSettingsStore.persist.hasHydrated()` is still `false` and the *real* persisted theme hasn't been applied yet — rendering the server-matching default until `hasHydrated()` flips avoids a hydration mismatch warning, then a one-time flash to the real theme once it resolves.

## 23. Calling `rehydrate()` manually with `skipHydration`

```typescript
const useSettingsStore = create<SettingsStore>()(
  persist((set) => ({ preferences: { theme: 'light' } }), {
    name: 'settings',
    skipHydration: true,
  }),
);

// Later, at a point your app controls (e.g. after a route transition):
useSettingsStore.persist.rehydrate();
```

**How it works:** `skipHydration: true` stops `persist` from calling its internal `hydrate()` automatically on store creation, leaving the initializer's plain defaults live until something calls `useSettingsStore.persist.rehydrate()` explicitly — useful in SSR frameworks where you want the server-rendered markup and the *first* client render to provably match (both showing defaults), only loading the real persisted state once you're certain it's safe (e.g. after the component tree that depends on it has mounted), trading one cycle of "wrong-looking" defaults for full control over exactly when the swap happens.

## 24. Listening for hydration completion with `onFinishHydration`

```typescript
const unsubscribe = useSettingsStore.persist.onFinishHydration((state) => {
  console.log('rehydrated preferences:', state.preferences);
  analytics.identify({ theme: state.preferences.theme });
});

// later, once no longer needed:
unsubscribe();
```

**How it works:** `onFinishHydration` (distinct from `onHydrate`, which fires *before* the storage read resolves) registers a callback invoked exactly once per `hydrate()` call, after `merge`'s result has already been committed via `set` — by the time this fires, `state.preferences` reflects whatever was actually loaded from storage, making it the right place for one-shot side effects that need the *final* rehydrated value (analytics identification, conditionally redirecting based on a persisted flag) rather than a `subscribe` listener, which would also fire on every later unrelated update.

## 26. Guarding against double-toggling a nested boolean during an in-flight async action

```typescript
interface FavoriteStore {
  favorites: Record<string, { pending: boolean; isFavorite: boolean }>;
  toggleFavorite: (id: string) => Promise<void>;
}

const useFavoriteStore = create<FavoriteStore>((set, get) => ({
  favorites: {},
  toggleFavorite: async (id) => {
    if (get().favorites[id]?.pending) return; // already in flight, ignore
    const current = get().favorites[id]?.isFavorite ?? false;
    set((state) => ({ favorites: { ...state.favorites, [id]: { pending: true, isFavorite: current } } }));
    const next = await api.toggleFavorite(id, !current);
    set((state) => ({ favorites: { ...state.favorites, [id]: { pending: false, isFavorite: next } } }));
  },
}));
```

**How it works:** the `pending` flag lives *inside* the same nested record as `isFavorite`, so the guard at the top of `toggleFavorite` reads it via `get()` synchronously before doing anything else — a second rapid click while the first call's `await` is still outstanding hits the guard and returns immediately, rather than firing a second overlapping request whose resolution order against the first is not guaranteed. This is the nested-state version of the stale-response guard from [Medium #10](./09-state-management-simplify-medium.mdx#10-async-actions), generalized to also prevent the *request* from being sent twice, not just prevent a late response from clobbering a fresher one.

## 27. Diffing nested state changes manually with `shallow` outside any subscription

```typescript
import { shallow } from '@headlesskit/state-management-simplify';

function describeChange(prev: { cart: { items: Item[] } }, next: { cart: { items: Item[] } }) {
  if (shallow(prev.cart, next.cart)) return 'cart unchanged';
  if (prev.cart.items.length !== next.cart.items.length) return 'item count changed';
  return 'item count same, contents changed';
}
```

**How it works:** `shallow(prev.cart, next.cart)` compares the two `cart` objects' own enumerable keys with `Object.is` one level deep — since `items` is itself a nested array, a shallow comparison treats *any* new `items` array reference as "different," even one produced by a no-op `.map()`, so `shallow` returning `false` here only tells you "the `cart` object or its `items` reference changed," not what changed inside `items`; distinguishing "count changed" from "contents changed at the same count" needs the explicit follow-up checks shown, because `shallow` itself doesn't recurse.

## 30. Detecting a hydration mismatch directly via `onRehydrateStorage`

## 32. Why patch-based replay is exact for nested *additive* updates but not nested *relative* ones

```typescript
// Additive (safe to skip/replay): each patch is independent of prior patches' values
toggleNotification('email');  // patch: { preferences: { notifications: { email: true } } }
toggleNotification('email');  // patch: { preferences: { notifications: { email: false } } }

// Relative (unsafe to skip/replay): patch encodes an absolute result of a relative op
multiplyFontSize(2);  // fontSize 14 -> 28, patch: { preferences: { fontSize: 28 } }
multiplyFontSize(2);  // fontSize 28 -> 56, patch: { preferences: { fontSize: 56 } }
// Skipping the first multiplyFontSize and keeping the second leaves fontSize at 56,
// not 28 (what re-running "multiply by 2" against the skipped state would give).
```

**How it works:** both examples record absolute resulting values as their patches (this package has no reducer, so there's nothing else *to* record — see [Example 4](#4-a-guided-time-travel-debugging-session)) — the difference is purely about whether replaying patches out of original order coincidentally still produces a *correct* result. Toggling a boolean is its own inverse regardless of order/skipping, so additive-in-spirit cases like it tolerate skip/sweep correctly; "multiply by 2" is relative to whatever value preceded it, so skipping an earlier multiplication and keeping a later one's *absolute* patch produces a value the real (non-skipped) action sequence would never have reached.

## 34. A nested-state store with optimistic update and structural rollback via immer

```typescript
const useBoardStore = create<{ board: { columns: Column[] } }>()(
  immer((set, get) => ({
    board: { columns: [] },
    moveTask: (taskId: string, fromCol: string, toCol: string) => {
      const snapshot = JSON.parse(JSON.stringify(get().board)); // deep snapshot for rollback
      set((state) => {
        const from = state.board.columns.find((c) => c.id === fromCol)!;
        const to = state.board.columns.find((c) => c.id === toCol)!;
        const idx = from.tasks.findIndex((t) => t.id === taskId);
        const [task] = from.tasks.splice(idx, 1);
        to.tasks.push(task);
      });
      api.moveTask(taskId, toCol).catch(() => set((state) => { state.board = snapshot; }));
    },
  })),
);
```

**How it works:** the rollback snapshot has to be a *deep* copy (`JSON.parse(JSON.stringify(...))`) rather than just `get().board` by reference, because the optimistic `set` immediately after mutates nested arrays in place via the immer draft — if the snapshot were a live reference into the same nested structure, the "before" copy would already reflect the "after" state by the time the network call's `.catch` tried to use it for rollback. This is the nested-immer equivalent of [Medium #9 of the simplify-medium examples](./09-state-management-simplify-medium.mdx#9-optimistic-updates-with-subscribe-based-error-recovery), generalized from "capture a reference" to "capture a deep copy," because immer's in-place draft mutation specifically invalidates the reference-capture trick that works fine for plain-spread updates.

## 38. A custom nested `merge` that deep-merges instead of shallow-replacing

```typescript
function deepMerge<T>(target: T, source: Partial<T>): T {
  const result = { ...target };
  for (const key of Object.keys(source) as (keyof T)[]) {
    const sv = source[key];
    result[key] = sv && typeof sv === 'object' && !Array.isArray(sv)
      ? deepMerge(target[key], sv as any)
      : (sv as T[keyof T]);
  }
  return result;
}

persist(initializer, {
  name: 'preferences',
  merge: (persisted, current) => deepMerge(current, persisted as object),
});
```

**How it works:** the default `merge` (`{ ...currentState, ...persistedState }`) only merges at the *top level* — exactly the [Basic #13](./08-state-management-simplify-basic.mdx#13-a-shallow-merge-gotcha-with-nested-objects) gotcha, but applied during rehydration instead of a normal `set`. If `partialize` only ever saved a subset of a nested object's fields (as in [Medium #14](./09-state-management-simplify-medium.mdx#14-persists-partialize-selecting-one-nested-sub-path)), the default `merge` would wholesale-replace that nested object on load and lose the unpersisted sibling fields; a recursive `deepMerge` for `merge` instead preserves fields at every nesting level that weren't part of what was persisted, restoring the same guarantee `partialize` alone can't provide on its own.

## 39. Why a `subscribeWithSelector` listener with `fireImmediately` matters for nested initial sync


**How it works:** without `fireImmediately`, the listener only runs on the *next* change to `user.preferences.theme` — the DOM attribute would stay unset (or stale) until something actually changes the theme, even though the store already has a real value for it right now. `fireImmediately: true` makes `subscribeWithSelector`'s implementation call the listener once synchronously at subscribe-time with `(currentSlice, currentSlice)` (same value as both arguments, since there's no real "previous" yet), syncing external systems like the DOM to nested store state immediately on setup rather than waiting for the first divergence.

## 43. Avoiding an infinite update loop from a selector that always returns a new nested object


## 45. Profiling: when `useShallow` costs more than it saves on a large nested object

```typescript
// Ten primitive fields nested under `profile` — useShallow does 10 Object.is checks every call
const profile = useStore(useShallow((state) => ({ ...state.profile })));

// Cheaper: select the one or two fields actually rendered
const { displayName, avatarUrl } = useStore(
  useShallow((state) => ({ displayName: state.profile.displayName, avatarUrl: state.profile.avatarUrl })),
);
```

**How it works:** `useShallow`'s comparator runs one `Object.is` check per own-enumerable-key on the returned object — spreading an entire ten-field nested object into the selector means ten comparisons on every store update, most of them comparing fields the component doesn't even render. Narrowing the selector to only the two fields actually used cuts that to two comparisons and, more importantly, means the component stops re-rendering at all for changes to the other eight fields — `useShallow` makes returning an object *safe*, but it doesn't make returning more fields than you need *free*.

```typescript
// store.ts
import { createStore, devtools, persist, unstable_ssrSafe, immer, createJSONStorage } from '@headlesskit/state-management-simplify';

interface AppStore {
  user: { profile: { name: string }; auth: { token: string | null } };
  cart: { items: { id: string; qty: number }[] };
}

export const makeAppStore = () =>
  createStore<AppStore>()(
    unstable_ssrSafe(
      devtools(
        persist(
          immer((set) => ({
            user: { profile: { name: '' }, auth: { token: null } },
            cart: { items: [] },
          })),
          { name: 'app', storage: createJSONStorage(() => localStorage), partialize: (s) => ({ user: { profile: s.user.profile } }) },
        ),
        { name: 'App' },
      ),
    ),
  );

// store.test.ts
test('cart item push via immer draft does not mutate the previous items array', () => {
  const store = makeAppStore();
  const before = store.getState().cart.items;
  store.setState((state) => { state.cart.items.push({ id: 'sku1', qty: 1 }); });
  expect(store.getState().cart.items).not.toBe(before);
});
```

**How it works:** the composition order resolves the same way as [Example 13](#13-three-middleware-composed-on-a-deeply-nested-multi-domain-store), with `unstable_ssrSafe` added as the new outermost layer — it's the one middleware here that needs to see whether it's running server-side *before* anything else in the stack does anything, since its entire job is to swap `api.setState` for a throwing stub when `typeof window === 'undefined'`, and that swap has to happen before `devtools`/`persist`/`immer` capture their own references to `set`. The test exercises the vanilla `createStore` form directly (no React, no `unstable_ssrSafe` triggering since `window` exists in the test environment) — the same "test the vanilla store, get the real component's logic for free" principle as [Example 6](#6-unit-testing-a-store-with-no-react-at-all) and [Example 18](#18-testing-a-nested-state-store-slice-in-isolation), now exercised against the full five-deep middleware-and-nesting stack instead of a bare store.
