# core/ internals (how createApi is actually built)

**Files:** `src/query/core/module.ts` (727 lines), `buildThunks.ts` (1124 lines), `buildSlice.ts` (735 lines), `buildInitiate.ts` (596 lines), `buildSelectors.ts` (413 lines), `core/index.ts`, plus `buildMiddleware/*` (index, types, batchActions, cacheCollection, cacheLifecycle, devMiddleware, invalidationByTags, polling, queryLifecycle, windowEventHandling)

None of these are imported directly in application code — [createApi](./01-create-api) is the only public entry point — but understanding the pipeline clarifies *why* RTK Query behaves the way it does. Roughly 3,500 lines implement everything described in [createApi](./01-create-api), [endpoint definitions](./05-endpoint-definitions), [api.util](./11-api-util), and [QueryStatus/state shape](./10-query-status-and-state-shape).

## The build pipeline, file by file

| File | Responsibility |
|------|-----------------|
| `module.ts` | The "core module" `createApi` is built from (via `buildCreateApi(coreModule())` — see [createApi](./01-create-api)). Wires every other piece below together, attaches `.util`, `.endpoints`, and per-endpoint `initiate`/`select`/`matchPending`/etc to the final `Api` object. |
| `buildThunks.ts` | Generates the actual async thunks dispatched under the hood for queries, mutations, and infinite queries — handles calling `baseQuery`, applying `transformResponse`/schema validation, generating `pending`/`fulfilled`/`rejected` actions (same three-action lifecycle as [createAsyncThunk](../06-create-async-thunk), purpose-built rather than reusing it directly since RTK Query needs additional metadata like `queryCacheKey`). |
| `buildSlice.ts` | The actual `createReducer`-style reducer for the whole api slice — processes every query/mutation lifecycle action into the `queries`/`mutations`/`provided`/`subscriptions`/`config` state shape documented in [QueryStatus and the state shape](./10-query-status-and-state-shape). |
| `buildInitiate.ts` | Builds each endpoint's `.initiate(arg, options)` — the dispatchable thunk a hook (or you, manually) calls to actually kick off a query/mutation. Handles cache-key deduplication (don't refetch if an identical request is already in flight or cached), subscription bookkeeping, and the `getRunningQueries`/`getRunningMutations` thunks. |
| `buildSelectors.ts` | Builds each endpoint's `.select(arg)` — a memoized selector reading that specific cache entry back out of state, deriving the `RequestStatusFlags` and the `isFetching` flag (distinct from `isLoading` — see [QueryStatus](./10-query-status-and-state-shape)) that hooks/components actually consume. |
| `setupListeners.ts` | Covered separately — see [setupListeners](./04-setup-listeners). |
| `core/index.ts` | Assembles `coreModule()` from all of the above. |

## `buildMiddleware/` — the actual runtime behavior engine

`api.middleware` (which you must add to your store — see [createApi](./01-create-api)'s pitfalls) is a composition of several independent "handlers," each watching the action stream for what it cares about:

| File | Watches for / drives |
|------|------------------------|
| `queryLifecycle.ts` | Runs each endpoint's `onQueryStarted` hook at the right moment, and resolves/rejects the `queryFulfilled` promise it's given. |
| `cacheLifecycle.ts` | Runs `onCacheEntryAdded`, tracking first-subscriber/last-unsubscriber transitions per cache key, and resolving `cacheEntryRemoved`/`cacheDataLoaded`. |
| `invalidationByTags.ts` | Watches for fulfilled mutations (and manual `api.util.invalidateTags` dispatches), cross-references `provided` tag state, and triggers refetches of matching queries — implementing both `invalidationBehavior` modes ([createApi](./01-create-api)). |
| `polling.ts` | Implements `pollingInterval` (a `SubscriptionOptions` field set per-hook-call) — schedules and re-triggers fetches on an interval for any query subscribed with polling enabled. |
| `cacheCollection.ts` | Implements `keepUnusedDataFor` — after a query's last subscriber unsubscribes, starts a timer; if no new subscriber appears before it elapses, removes the cache entry entirely (garbage collection). |
| `batchActions.ts` | Coalesces multiple state-changing actions dispatched in the same tick into fewer subscriber notifications — conceptually similar in spirit to [autoBatchEnhancer](../09-auto-batch-enhancer), but specific to RTK Query's own action stream. |
| `windowEventHandling.ts` | Reacts to the `onFocus`/`onOnline` actions [setupListeners](./04-setup-listeners) dispatches, triggering `refetchOnFocus`/`refetchOnReconnect` behavior. |
| `devMiddleware.ts` | Development-only sanity checks (e.g. warns if `api.middleware` was never actually added to the store, the single most common setup mistake — see [createApi](./01-create-api)'s pitfalls). |
| `types.ts` | Shared internal types for the handler-builder pattern above (`InternalHandlerBuilder`, `BuildMiddlewareInput`, etc) — not part of the public API. |

## Why this is structured as many small "handlers" composed into one middleware

Each handler in `buildMiddleware/` is built independently (`build*Handler(input)`) and then composed by `core/buildMiddleware/index.ts` into the single `api.middleware` function — this separation exists so each piece of automatic behavior (polling vs. cache GC vs. tag invalidation, etc) is independently testable and reasoned about, while still ultimately presenting as one middleware function to `configureStore`. None of these individual handler-builders are exported from the package — only the assembled whole (`api.middleware`) is public.

## Common pitfalls

- **Don't try to import or call any `core/` file directly** — `module.ts`/`buildThunks.ts`/etc are wired together with internal-only types and mutable closures specific to one `createApi` call; there is no supported way to use pieces of this pipeline standalone outside of `createApi` itself.
- **If you're debugging unexpected RTK Query behavior (a query refetching when you didn't expect, or not refetching when you did), the relevant logic almost always lives in exactly one of the `buildMiddleware/` handlers above** — knowing which one narrows the search dramatically: refetch-on-focus issues are in `windowEventHandling.ts`, tag-invalidation timing issues are in `invalidationByTags.ts`, stale cache not clearing is `cacheCollection.ts`, and so on.
