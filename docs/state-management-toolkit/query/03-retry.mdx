# retry

**File:** `src/query/retry.ts`

A `baseQuery` **enhancer** — wraps any existing `baseQuery` (most commonly [fetchBaseQuery](./02-fetch-base-query)) to automatically retry failed requests with exponential backoff, before giving up and surfacing the error.

## Signature

```typescript
function retry(baseQuery: BaseQueryFn, defaultOptions?: RetryOptions): BaseQueryFn
retry.fail(error, meta?): never // see below
```

| Option | Type | Default | Description |
|--------|------|---------|--------------|
| `maxRetries` | `number` | `5` | How many retry attempts before giving up. Mutually exclusive with `retryCondition` (TypeScript enforces only one is set). |
| `retryCondition` | `(error, args, { attempt, baseQueryApi, extraOptions }) => boolean` | `attempt <= maxRetries` | Full control over whether to retry — return `false` to stop early (e.g. don't retry a `401 Unauthorized`, since retrying won't help), or implement your own attempt-count logic. |
| `backoff` | `(attempt, maxRetries, signal?) => Promise<void>` | exponential backoff: roughly `300ms * 2^attempt`, randomized between 0.4x–1.4x, capped at `maxRetries` | Customize the delay strategy between attempts — e.g. linear backoff, or a fixed delay. |

Both `defaultOptions` (set once when wrapping the base query) and per-endpoint `extraOptions` are merged, with the endpoint's `extraOptions` taking precedence — letting you set a sane app-wide default and override it for specific endpoints that need more or fewer retries.

## How it decides whether to keep retrying

1. Calls the wrapped `baseQuery`. If it resolves with no `error` field, returns immediately — success.
2. If it errors, increments the attempt counter and checks `retryCondition(error, args, { attempt, ... })`.
3. If `retryCondition` returns `true`, waits via `backoff(attempt, maxRetries, signal)`, then loops back to step 1.
4. If `retryCondition` returns `false` (or an unexpected, non-base-query error exceeds `maxRetries`), returns the error as the final result — the caller (your endpoint, then your component) sees it exactly as if no retry had happened, just later.
5. **Aborting** (the query's `AbortSignal` firing — e.g. a component unmounting mid-retry) immediately stops the loop at the next checkpoint, without waiting out the remaining backoff delay.

## `retry.fail(error, meta?)` — opting an error out of retries from inside `queryFn`

If you're using a custom `queryFn` (not just a plain `query` URL/object) wrapped by `retry`, and you know a particular failure should **never** be retried (e.g. a validation error from your own code, not a transient network/server issue), call `retry.fail(...)` instead of returning `{ error }` — it throws a special marker the retry loop recognizes and respects immediately, skipping `retryCondition` entirely.

```typescript
import { retry } from '@headlesskit/state-management-toolkit/query';

const baseQueryWithRetry = retry(fetchBaseQuery({ baseUrl: '/api' }));

const api = createApi({
  baseQuery: baseQueryWithRetry,
  endpoints: (builder) => ({
    getPost: builder.query<Post, { id: number }>({
      async queryFn({ id }, api, extraOptions, baseQuery) {
        if (id < 0) {
          retry.fail({ status: 'CUSTOM_ERROR', error: 'Invalid id, will never succeed' });
        }
        return baseQuery(`/post/${id}`);
      },
    }),
  }),
});
```

## Basic usage

```typescript
import { createApi, fetchBaseQuery, retry } from '@headlesskit/state-management-toolkit/query';

const staggeredBaseQuery = retry(fetchBaseQuery({ baseUrl: '/' }), { maxRetries: 5 });

export const api = createApi({
  baseQuery: staggeredBaseQuery,
  endpoints: (build) => ({
    getPosts: build.query<Post[], void>({ query: () => 'posts' }),
    getPost: build.query<Post, string>({
      query: (id) => `post/${id}`,
      extraOptions: { maxRetries: 8 }, // overrides the default for just this endpoint
    }),
  }),
});
```

## Advanced: skip retrying client errors, only retry server/network errors

```typescript
const baseQueryWithRetry = retry(fetchBaseQuery({ baseUrl: '/api' }), {
  retryCondition: (error, _args, { attempt }) => {
    if (typeof error.status === 'number' && error.status >= 400 && error.status < 500) {
      return false; // 4xx errors are the client's fault — retrying won't fix a bad request or expired auth
    }
    return attempt <= 3; // retry network errors / 5xx up to 3 times
  },
});
```

## Common pitfalls

- **Retrying mutations is usually wrong by default** — a mutation that "failed" due to a network blip *after* the server already processed it (e.g. response lost in transit) being retried can duplicate side effects (double-charging, duplicate row creation). Consider a narrower `retryCondition` for mutation endpoints, or skip wrapping mutations in `retry` entirely, depending on whether your backend is idempotent for that operation.
- **`maxRetries` and `retryCondition` are mutually exclusive in the type system** — supplying both is a type error; if you need both an attempt cap *and* custom logic, fold the cap into your own `retryCondition` (`attempt <= yourMax && yourOtherLogic`).
- **The default backoff delay grows fast** — by the 5th default retry, the delay is already several seconds; for latency-sensitive UI, consider a lower `maxRetries` or a custom linear `backoff` rather than the default exponential curve.
